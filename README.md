# Тестовое задание - Intern QA

## 1. Будильник

### Вопросы к продукт-менеджеру

1. В первом требовании выбираются дни недели, а во втором для одноразового будильника нужна дата. При выборе одноразового режима дни недели заменяются календарём? Что делать, если дата уже прошла?
2. Когда именно одноразовый будильник отключается: при первом уведомлении или после stop? Если сразу при срабатывании, должен ли после этого работать snooze?
3. Откуда берётся N: это фиксированный интервал или настройка пользователя? Какие значения допустимы?
4. Что такое зона «долгого сна»: отдельный режим или промежуток времени? Пять повторов - это пять нажатий snooze после первого сигнала? Что происходит при попытке отложить шестой раз?
5. Что делать при переходе часов вперёд, если выбранного времени в этот день нет? А при переходе назад, если одно и то же время наступит дважды?
6. Если выключить будильник, пока он отложен, отменяется ли уже запланированное уведомление snooze?
7. Что означает stop для повторяющегося будильника: завершить текущее срабатывание или полностью выключить расписание?
8. Должен ли будильник срабатывать при закрытом приложении и заблокированном телефоне? Как сообщать пользователю, что разрешение на уведомления не выдано?

### Smoke-чек-лист

P0 - проверил бы в первую очередь, P1 - сразу после основных сценариев. Для проверки беру обычный день без перевода часов, уведомления разрешены.

| Приоритет | Проверка | Ожидаемый результат |
|---|---|---|
| P0 | Создать одноразовый будильник на будущую дату, 07:30 | Будильник сохранён и виден в списке с выбранной датой и временем |
| P0 | Дождаться указанной даты и 07:30 | Появилось уведомление, одноразовый будильник автоматически отключён; точный момент отключения уточняется |
| P0 | Создать повторяющийся будильник на понедельник и среду, 08:00; проверить понедельник, вторник и среду | В выбранные дни уведомление появляется, во вторник - нет |
| P0 | Выключить активный будильник до назначенного времени | Запись остаётся в списке, уведомление по расписанию не появляется |
| P0 | Включить его обратно до следующего выбранного времени | В ближайшее выбранное время появляется уведомление |
| P0 | При срабатывании нажать stop | Текущее срабатывание завершено; судьбу повторяющегося расписания сверить с ответом на вопрос 7 |
| P0 | При срабатывании нажать snooze один раз | Повторное уведомление через согласованные N минут |
| P1 | Создать повторяющийся будильник «каждый день» на 09:00 | За неделю уведомление появляется в 09:00 во все семь дней |

### Техники тест-дизайна

**Граничные значения.** Для времени проверю 00:00, 00:01, 23:58 и 23:59. Если поле позволяет вводить текст, добавлю 24:00, 12:60 и отрицательный час: это недопустимое время в заданном формате. Для выбора времени через прокрутку проверю, что такие значения нельзя выбрать. Это проверка границ часов и минут, где легко ошибиться на единицу.

Для «долгого сна» отдельно проверю первый, второй и третий snooze: после каждого нажатия уведомление должно повторяться через N минут.

**Таблица решений.** Возьму повторяющийся будильник на понедельник и среду, 08:00. Во всех строках текущее время 08:00, нет отложенного уведомления и перевода часов.

| Будильник включён | День выбран | Пример | Уведомление |
|---|---|---|---|
| Да | Да | Понедельник | Есть |
| Да | Нет | Вторник | Нет |
| Нет | Да | Среда | Нет |
| Нет | Нет | Четверг | Нет |

**Переходы состояний.** Проверю цепочку: включён → сработал → отложен → снова сработал → stop. При каждом переходе смотрю уведомление и состояние записи в списке. Дополнительно пройду включён → выключен → включён без удаления записи. Для одноразового будильника особенно важен переход после первого срабатывания: автоматическое отключение не должно случайно сделать согласованный сценарий snooze невозможным.

### Рискованный сценарий

На тестовом устройстве настроен переход назад с 03:00 на 02:00. Одноразовый будильник стоит на 02:30 в эту дату. При первом наступлении 02:30 пользователь нажимает stop. После перевода часов 02:30 наступает ещё раз.

По требованиям будильник должен сработать один раз и отключиться. Иначе пользователь получит второй сигнал от уже завершённого будильника. Обычная проверка в день без перевода часов этого не обнаружит.

## 2. Создание заказа

### Вопросы к команде

1. Какие типы и допустимые значения у `user_id` и `product_id`? Что возвращать для несуществующего пользователя? Для товара описан 404, для пользователя такого правила нет.
2. Какую ошибку возвращать, если проблем несколько: например, в одной позиции `quantity: 0`, а другой товар не существует? Есть ли установленный порядок проверок?
3. Если в `items` два раза передать `product_id: 101`, количества складываются, позиции остаются отдельными или это ошибка?
4. Если товара достаточно для одной позиции, но недостаточно для второй, отклоняется весь заказ? Может ли остаться частичный заказ или резерв?
5. Как выглядит тело ошибки и как называются поля успешного ответа? Указаны идентификатор и статус, но нет схемы ответа.
6. Есть ли максимальное количество единиц товара и позиций? Какой таймаут у сервиса остатков и есть ли внутренние повторные обращения?

| 1 | Базовый запрос | 201, идентификатор заказа и статус `created` | 1–4 |
| 2 | `quantity: 1` | 201: минимальное положительное целое | 3, 4 |
| 3 | Удалить `user_id` из запроса | 400 | 1, 5 |
| 4 | Удалить `items` из запроса | 400 | 1, 5 |
| 5 | Передать `items: []` | 400 | 1, 5 |
| 6 | Удалить `product_id` из единственной позиции | 400 | 2, 5 |
| 7 | Удалить `quantity` из единственной позиции | 400 | 2, 5 |
| 8 | Отправить `quantity: 0` | 400 | 3, 5 |
| 9 | Установить остаток 101 равным 2, заказать 2 | 201: ровно необходимое количество есть | 4 |
| 10 | Установить остаток 101 равным 1, заказать 2 | 409 | 7 |

| 12 | Отправить базовый запрос при недоступном сервисе остатков | 503 | 8 |

### Тест-кейс 1. Успешное создание

**Предусловия:** пользователь 15 существует, товар 101 существует, доступный остаток равен 5. Сервис остатков отвечает. Другие заказы не меняют этот остаток во время проверки.

**Запрос:** `POST /orders`, `Content-Type: application/json`.

```json
{
  "user_id": 15,
  "items": [
    {"product_id": 101, "quantity": 2}
  ]
}
```

**Действия:** отправить запрос один раз, сохранить ответ и проверить созданный заказ по возвращённому идентификатору через доступный на стенде способ чтения.

**Ожидается:** HTTP 201. Ответ содержит идентификатор и статус `created`. Сохранённый заказ относится к пользователю 15, содержит товар 101 в количестве 2. Название поля идентификатора сверю со схемой API, в условии его нет.

### Тест-кейс 2. Нулевое количество

**Предусловия:** пользователь 15 и товар 101 существуют, остаток 5, сервис остатков доступен. Остальные условия корректны, чтобы проверить именно количество.

**Запрос:** `POST /orders`, `Content-Type: application/json`.

```json
{
  "user_id": 15,
  "items": [
    {"product_id": 101, "quantity": 0}
  ]
}
```

**Действия:** отправить запрос, проверить ответ и наличие нового заказа на стенде.

**Ожидается:** HTTP 400 по требованиям 3 и 5. Заказ с нулевым количеством не должен создаваться. Точный текст ошибки не проверяю без согласованного формата.

### Тест-кейс 3. Недоступен сервис остатков

**Предусловия:** пользователь 15 и товар 101 существуют. На тестовом стенде зависимость проверки остатков подменена заглушкой, имитирующей недоступность соединения. Сам API заказов работает, запрос корректен.

**Запрос:** `POST /orders`, `Content-Type: application/json`.

```json
{
  "user_id": 15,
  "items": [
    {"product_id": 101, "quantity": 2}
  ]
}
```

**Действия:** включить сбой заглушки, отправить запрос, получить ответ. По журналу тестовой заглушки убедиться, что API действительно обратился к зависимости. После проверки восстановить её работу.

**Ожидается:** HTTP 503 по требованию 8. Система не должна сообщать об успешном создании без проверки доступности товара. Возможность сохранения промежуточной записи и её статус нужно уточнить: из требования про 503 нельзя вывести, что в базе вообще не останется записей.

### Почему одного HTTP-статуса мало

201 может прийти, даже если в сохранении данных есть ошибка: например, заказ записали на другого пользователя или сохранили количество 1 вместо 2.

Проверю идентификатор и `created` в ответе, затем саму запись заказа: пользователя 15, товар 101, количество 2. Для чтения использую предусмотренный на стенде API или доступ к тестовой БД; конкретный endpoint чтения в условии не задан. Также проверю, что один запрос не создал два заказа. Если при создании резервируется остаток, проверю резерв двух единиц, но сначала уточню, происходит резервирование здесь или на следующем шаге.

### Повторный запрос после обрыва соединения

Обрыв ответа ещё не означает, что заказ не создался. Первый запрос мог успешно завершиться на сервере. Повторный тогда создаст второй заказ, а при наличии резервирования ещё раз займёт товар на складе.

У команды спрошу:

- Есть ли защита от повторного создания, например ключ идемпотентности?
- Как долго хранится результат по ключу и привязан ли ключ к пользователю?
- Что вернётся при одинаковом ключе с другим количеством товара?
- Как клиент может узнать результат первого запроса?

Предложил бы проверить обрыв в двух точках: до сохранения заказа и после сохранения, но до доставки ответа клиенту. Повторить запрос и сравнить количество заказов и резервов. Если ключ идемпотентности поддерживается, запросы с одним ключом должны относиться к одной операции. Точные статусы повторного ответа нужно брать из согласованного контракта.

Просто запретить одинаковое тело запроса нельзя: пользователь может намеренно заказать такой же товар ещё раз. Для проверки такого случая нужны две отдельные операции с разными ключами. Здесь используется сценарный подход и разделение по моменту сбоя: одинаковая ошибка у клиента может скрывать разное состояние на сервере.

## 3. SQL

### 3.1. Пользователи из Москвы

```sql
SELECT id, name, city, created_at
FROM users
WHERE city = 'Москва'
ORDER BY id;
```

Результат: Анна (1) и Виктор (3).

### 3.2. Сумма оплаченных заказов по каждому пользователю

```sql
SELECT u.id, u.name, COALESCE(SUM(o.total), 0) AS paid_total
FROM users AS u
LEFT JOIN orders AS o
    ON o.user_id = u.id AND o.status = 'completed'
GROUP BY u.id, u.name
ORDER BY u.id;
```

| id | name | paid_total |
|---|---|---|
| 1 | Анна | 3000 |
| 2 | Борис | 2500 |
| 3 | Виктор | 1500 |
| 4 | Глеб | 0 |

Фильтр статуса оставляю в `ON`: если поставить его в `WHERE`, Глеб пропадёт из результата. `COALESCE` нужен для нуля вместо `NULL`.

### 3.3. Есть хотя бы один возвращённый заказ

```sql
SELECT u.id, u.name
FROM users AS u
JOIN orders AS o ON o.user_id = u.id
GROUP BY u.id, u.name
HAVING SUM(CASE WHEN o.status = 'returned' THEN 1 ELSE 0 END) > 0
ORDER BY u.id;
```

Результат: Виктор (3), у него заказ 105 со статусом `returned`. `HAVING` оставляет группы, где найден хотя бы один возврат, и пользователь выводится один раз.

### 3.4. Топ-3 по сумме оплаченных заказов

```sql
SELECT u.id, u.name, COALESCE(SUM(o.total), 0) AS paid_total
FROM users AS u
LEFT JOIN orders AS o
    ON o.user_id = u.id AND o.status = 'completed'
GROUP BY u.id, u.name
ORDER BY paid_total DESC, u.id
LIMIT 3;
```

Результат: Анна — 3000, Борис — 2500, Виктор — 1500. При равных суммах использую id для стабильного порядка и вывожу ровно три строки. Если нужно включать всех с одинаковой суммой на третьем месте, правило надо уточнить.

### 3.5. Пользователи без единого заказа

```sql
SELECT u.id, u.name
FROM users AS u
LEFT JOIN orders AS o
    ON o.user_id = u.id AND o.status = 'completed'
WHERE o.id IS NULL
ORDER BY u.id;
```

Результат: Глеб (4).

### 3.6. Средняя сумма одного оплаченного заказа по городам

```sql
SELECT u.city, AVG(DISTINCT o.total) AS avg_paid_order
FROM users AS u
LEFT JOIN orders AS o
    ON o.user_id = u.id AND o.status = 'completed'
GROUP BY u.city
ORDER BY u.city;
```

| city | avg_paid_order |
|---|---|
| Казань | NULL |
| Москва | 2250 |
| СПб | 2500 |

Для Москвы: `(3000 + 1500) / 2 = 2250`. Это среднее по отдельным оплаченным заказам, не среднее по суммам пользователей. Для Казани оставляю `NULL`: оплаченных заказов нет и среднее не определено.
